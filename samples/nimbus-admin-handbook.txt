Nimbus workspace administration handbook

This handbook is for people who manage a Nimbus workspace for a team. It covers inviting members, setting permissions, managing storage, reviewing the audit log, and handling the most common support requests. It assumes you already know how to use the Nimbus CLI as an ordinary member; if not, read the Nimbus CLI Guide first.

Every workspace has at least one owner. Owners can do everything an administrator can, and in addition they can delete the workspace, transfer ownership, and change the billing plan. We recommend having exactly two owners, so that the workspace is never locked if one person leaves the company or loses access to their account. Administrators manage members and settings but cannot delete the workspace or see billing details.

To invite a member, open the web app, go to Members, and choose Invite. Enter one email address per line; you can paste up to 200 addresses at once. Each person receives an invitation that stays valid for 14 days. If an invitation expires, send a new one from the same page; the old link stops working as soon as a new one is sent. Invited people who already have a Nimbus account join immediately after accepting. People without an account are asked to create one first, using the same email address the invitation was sent to.

Permissions are set per folder, not per file. A member can be a viewer, an editor, or a manager of a folder. Viewers can download files but cannot change them, and the CLI syncs viewer folders in read-only mode, so local edits are never uploaded. Editors can add, change, and delete files. Managers can do everything editors can, and they can also change who has access to the folder. Permissions are inherited by subfolders unless a subfolder has its own settings, in which case the subfolder settings replace the inherited ones completely rather than adding to them. This catches many administrators out: if you give a subfolder its own list of editors, people who only had access through the parent folder lose access to that subfolder. The web app shows a small padlock icon next to folders with their own settings, so they are easy to find. When a member is removed from the workspace, their access to every folder ends at once, but files they uploaded stay in place and keep their version history. Their CLI stops syncing at the next poll and reports error NMB-1001, because the workspace is no longer available to them. Local copies on their computer are not deleted, so if the files are sensitive you should ask them to delete the synced folder, or use your company's device management tools to do it.

Storage is shared by the whole workspace. The current usage and the plan limit are shown on the Storage page, along with the twenty largest folders. When usage reaches 90 percent of the limit, owners and administrators receive an email warning. When it reaches 100 percent, uploads stop and the CLI reports error NMB-3007 for every file it tries to upload, but downloads and deletes keep working so that members can free up space. Files in the trash count toward the limit until they are removed permanently, which happens automatically after 30 days. To free space immediately, empty the trash from the Storage page. Old file versions also count toward the limit. By default Nimbus keeps every version for 90 days; you can shorten this to 30 days on the Storage page, which usually frees a large amount of space in workspaces with frequently edited files.

The audit log records every sign-in, invitation, permission change, and deletion in the workspace. Each entry shows who did it, when, from which IP address, and whether it was done in the web app, the CLI, or the API. Entries are kept for one year. You can filter the log by person, by folder, or by type of action, and export any filtered view as a CSV file for your security team. File edits are not in the audit log, because they are recorded in each file's version history instead. If you need to find out who deleted a file, search the audit log for the file name and filter by the Deletion action; the entry also tells you whether the file is still in the trash and can be restored.

The most common support request is a member who says that their changes are not appearing for everyone else. In most cases the member has viewer permission on the folder, so the CLI is syncing it in read-only mode and quietly keeping their edits local. Check their permission on the folder first. The second most common cause is an exclude pattern in their nimbus.toml file that matches the files they are editing; ask them to run "nimbus status --why" followed by the file name, which prints the rule that stopped the upload. The third cause is a conflict: if the same file was changed by two people between syncs, Nimbus keeps both copies and saves the other version next to the original with ".remote" added before the extension, logging error NMB-4012. The member may be looking at the wrong copy.

Another frequent request is from members who cannot sign in after changing their email address. Nimbus accounts are tied to the email address, so the member must be invited again using the new address. Their old account keeps the files it uploaded, and an owner can transfer those files to the new account from the Members page by choosing the old account and selecting Transfer files. The transfer keeps version history, folder locations, and permissions.

Finally, remember that administrators cannot see members' passwords or reset them directly. If a member is locked out, send them to the sign-in page and ask them to choose Forgot password. If your company uses single sign-on, password resets are handled by your identity provider instead, and Nimbus support cannot help with them.
