## How to read the results

- **Modes**: all = All uploads; one = the question's `upload`; wrong = the question's
  `wrongUpload` (should be "not found").
- **Pass**: an answerable question is answered and a cited chunk contains one of its
  `expect` phrases (broad: cites a chunk from the expected upload); everything else comes
  back "not found". Not checked automatically, so read the answers: coverage for broad
  questions, and for partial ones whether the missing part is named.
- **Top score**: the best chunk's score from the search. Below the threshold, the reply
  is "not found" without calling the LLM; at or above it, the LLM decides.
- **Diagnosis** of a Fail: threshold (answerable, but below it), retrieval (the expected
  fact wasn't in the chunks sent), prompt/LLM (it was, or there was no answer to give).
- **Notes** flag replies worth a look even when they pass.

### mongodb-advantages (all): Pass, top score 0.8588

**Q:** What are the advantages of the document model over relational databases?

*Note in test-questions.json:* The answer spans five small chunks, one per advantage.

> The uploads list these advantages of the document model over relational databases:
>
> - **Documents map to objects in code:** A document looks like the object your application already works with, so there is no object-relational mapping layer and no need to reassemble an object from several result sets. [1]
> - **Data read together is stored together:** Reading an order takes one lookup by `_id` with no joins, whereas a normalized relational schema needs a query that joins several tables. For read-heavy workloads with a clear access pattern, one document per read is simpler and usually faster. [2]
> - **Flexible schema:** Documents in the same collection don't need identical fields, and you can add a field without a migration that locks or rewrites a large table. [3] A collection can still enforce rules such as required fields, types and allowed values through JSON Schema validation. [3]
> - **Horizontal scaling:** MongoDB scales out by sharding, which splits a collection across servers by a shard key. Because related data sits in one document, most operations touch one shard. Scaling a relational database across servers is possible but harder, because joins and foreign keys assume the rows live together. [4]
> - **High availability:** A replica set keeps copies of the data on several servers. If the primary fails, the remaining members elect a new primary automatically, usually within seconds, and drivers reconnect without application changes. [5]
>
> The uploads also note that relational databases remain a strong choice when data is highly interconnected and queried in many unpredictable ways, when most operations must update many entities at once in transactions, or when a team relies on existing SQL tooling and reporting. [6]

### mongodb-advantages (one): Pass, top score 0.8588

**Q:** What are the advantages of the document model over relational databases?

*Note in test-questions.json:* The answer spans five small chunks, one per advantage.

> The document model has these advantages over relational databases:
>
> - **Data read together is stored together.** Reading an order takes one lookup by `_id`, with no joins, whereas a normalized relational schema needs a query that joins several tables. [1] For read-heavy workloads with a clear access pattern, one document per read is simpler and usually faster. [1]
> - **Documents map to objects in code.** There is no object-relational mapping layer and no need to reassemble an object from several result sets, which removes a whole category of code and bugs. [2]
> - **Flexible schema.** Documents in a collection don't need identical fields, and you can add a field without a migration that locks or rewrites a large table. [3] A collection can still enforce rules such as required fields, types and allowed values with JSON Schema validation. [3]
> - **Horizontal scaling.** MongoDB scales out by sharding, splitting a collection across servers by a shard key. Because related data sits in one document, most operations touch one shard. [4] Scaling a relational database across servers is possible but harder, because joins and foreign keys assume the rows live together. [4]
> - **High availability.** A replica set keeps copies of the data on several servers. If the primary fails, the remaining members elect a new primary automatically, usually within seconds, and drivers reconnect without application changes. [5]
>
> The uploads also say that relational databases remain a strong choice when data is highly interconnected and queried in many unpredictable ways, when most operations update many entities at once in transactions, or when a team relies on existing SQL tooling and reporting. [6]

> - For the contrast-top version, sew the contrast top to the exterior bottom panel with a 3/8" seam allowance. Press the seam toward the contrast top and topstitch along it. [1]
> - Apply fusible fleece to the wrong side of both exterior pieces. [2]

> 3. Attach the second exterior piece to the other side of the zipper and baste it, then repeat the lining step with the second lining piece. [5]
> 4. Pull the lining away from one exterior piece, clip it to the other lining piece, and topstitch 1/8" from the zipper edge of that exterior piece only. Do this on both sides of the zipper. [5]
