### broad-mongodb-schema-design (all): Pass, top score 0.8385

**Q:** What should I consider when designing a MongoDB schema?

*Note in test-questions.json:* Spread over several sections: embed or reference, design patterns, anti-patterns, indexes, transactions.

> **Core rule:** Data that is accessed together should be stored together. [1] For read-heavy workloads with a clear access pattern, one document per read is simpler and usually faster. [1]
>
> **Flexibility with validation:** Documents in the same collection don't need identical fields, but a collection can enforce rules with JSON Schema validation, such as required fields, types and allowed values. [2]
>
> **Patterns to consider:**
> - Bucket: group many small items into one document per time window. [3]
> - Computed: store an expensive-to-calculate value and update it on write. [3]
> - Subset: keep the most-used part of a large list in the main document and the rest in a separate collection. [3]
> - Attribute: turn many optional fields into an array of key-value pairs so one index covers them. [3]
> - Outlier: handle rare exceptional documents with an overflow document and a flag. [3]
> - Schema versioning: add a `schemaVersion` field so old and new shapes can coexist during gradual migration. [3]
>
> **Anti-patterns to avoid:**
> - Unbounded arrays, which keep growing toward the 16 MB limit and slow every read. Use referencing or the bucket pattern instead. [4]
> - Treating MongoDB like a relational database, such as splitting every entity into its own collection and using `$lookup` on every read. [4]
> - Too many collections, which waste memory. Prefer fewer collections with a field that distinguishes the kinds. [4]
> - Unnecessary indexes, which slow writes and use memory. `$indexStats` shows how often each is used. [4]
> - Case-insensitive regex queries, which can't use an index efficiently. Create an index with a case-insensitive collation instead. [4]
