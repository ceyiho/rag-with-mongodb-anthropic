## How to read the results

- **Modes**: all = All uploads; one = the question's `upload`; wrong = the question's
  `wrongUpload` (should be "not found"); several = the uploads in its `several` list,
  ticked together (an answer is expected if one of them answers the question).
- **Pass**: an answerable question is answered and a cited chunk contains one of its
  `expect` phrases (broad: cites a chunk from the expected upload); everything else comes
  back "not found". Not checked automatically, so read the answers: coverage for broad
  questions, and for partial ones whether the missing part is named.
- **Top score**: the best chunk's score from the search. Below the threshold, the reply
  is "not found" without calling the LLM; at or above it, the LLM decides.
- **Diagnosis** of a Fail: threshold (answerable, but below it), retrieval (the expected
  fact wasn't in the chunks sent), prompt/LLM (it was, or there was no answer to give).
- **Notes** flag replies worth a look even when they pass.

> What to look for in the output:
> - **Stage and index name:** An `"stage" : "IXSCAN"` element in the `$queryPlanner` metadata, along with the `indexName` (for example `"customer_id_1"`, shows that an index was used. [2]

>

>

> - The main rule of document design is that data accessed together should be stored together. [1] For read-heavy workloads with a clear access pattern, one document per read is simpler and usually faster. [1]
>
> **Embed or reference**
> - Embed when the related data is read with the parent most of the time, belongs to the parent with no life of its own, and the number of items is small and bounded. [2]
> - Reference when the data is large or often read on its own, shared by many parents, or can grow without limit. [2]
> - The extended reference pattern is a middle ground: store the `_id` plus the few fields you display most often. The cost is that copied fields must be updated in both places if they change. [2]
> - If every read needs a `$lookup`, the data probably should have been embedded. [2]
>
> **Schema design patterns**
> - Bucket (group many small items into one document per time window), computed (store expensive values and update on write), subset (keep the most-used part in the main document), attribute (turn optional fields into key-value pairs so one index covers them), outlier (handle rare exceptions with an overflow document), and schema versioning (a `schemaVersion` field so old and new shapes coexist). >

> - Documents in a collection don't need identical fields, but a collection can still enforce rules with JSON Schema validation (`$jsonSchema`), such as required fields, types and allowed values. [4]

> - Without an index, a query scans every document in the collection. For compound indexes, follow the ESR guideline: Equality fields first, then Sort, then Range. [5]
> - Every index slows down writes and uses memory, so remove indexes that no query uses. [6]

> - Unbounded arrays, treating MongoDB like a relational database (splitting everything into collections and joining with `$lookup`), too many collections, unnecessary indexes, and case-insensitive regex queries without a collation index. [6]

> **Whether a document model fits**
