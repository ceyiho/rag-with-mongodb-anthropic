>   - Embed when the related data is usually read with the parent, belongs to it, and is small and bounded. [2]
>   - Reference when the data is large or often read alone, shared by many parents, or can grow without limit. [2]
>   - If every read needs a `$lookup`, the data probably should have been embedded. [2]

> - **Validation:** Flexible doesn't mean unvalidated. A collection can enforce required fields, types and allowed values with JSON Schema validation. [4]
> - **Indexes:** Without an index, a query scans every document in the collection. For compound indexes, put Equality fields first, then Sort fields, then Range fields. [5] Every index slows writes and uses memory, so remove unused ones. [6]
> - **Anti-patterns to avoid:**
>   - Unbounded arrays, which push the document toward the 16 MB limit. [6]
>   - Treating MongoDB like a relational database, with a collection per entity and `$lookup` on every read. [6]
>   - Too many collections. [6]
>   - Case-insensitive regex queries without a collation index. [6]
> - **Fit:** Relational databases remain strong when data is highly interconnected and queried in unpredictable ways, or when most operations update many entities in transactions. Document databases shine when access patterns are known, objects are hierarchical, the schema evolves quickly, or the data must scale across many servers. [7]

> The book outlines three crucial tips [1], and says to use the explain plan to identify opportunities for optimisation, typically once the pipeline is functionally correct [1].
>
> 1. **Be aware of streaming vs blocking stage ordering.** The sort-related advice falls under this tip:
>    - Use an index sort: if the $sort doesn't depend on a preceding $unwind, $group or $project, move it near the start so it can use an index and avoid an expensive in-memory sort. [2]
>    - Use $limit directly after $sort if you only need the first subset of records, so the sort only has to track that many records in memory. [2]
>    - Otherwise, move $sort as late as possible and make sure earlier stages significantly reduce the number of records reaching it. [2]
>
> 2. **Avoid unnecessary $unwind/$group combinations.** You should never need $unwind/$group to transform an array field's elements for each document in isolation. [3] Otherwise, execution time can increase by an order of magnitude once the blocking group stage handles more than 100 MB of in-flight data. [3]
>
> 3. **Encourage $match filters to appear early.** Top-level $match content forms part of the initial query filter, which gives the aggregation the best chance of using an index. [3] If a $match depends on a computed value, you can try these:
>    - Rework the filter so it checks the original field, which lets the engine push it to the top and use an index. [4]
>    - Add an extra partial $match at the top of the pipeline that targets the original field. [4]
>
> For sharded clusters, try to target the aggregation at one shard by including a $match on a shard key value (or prefix) [5]. Also, where a split pipeline could merge on a mongos, avoid specifying allowDiskUse:true if possible. [5]
