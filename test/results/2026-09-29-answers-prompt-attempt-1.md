**Q:** My laptop battery drains fast because Nimbus checks for changes too often. What can I change?

*Note in test-questions.json:* poll_interval in nimbus.toml; never says 'poll'.

> Raise the `poll_interval` setting in your `nimbus.toml`.
>
> - `poll_interval` controls how often Nimbus asks the server for remote changes. Lower values make changes appear sooner but use more battery and bandwidth. [1] A higher value means fewer checks and less battery use.
> - The default is 30 seconds, and values below 10 seconds are rejected with error NMB-2201. [1] If you've set it low, increase it above that.
> - The setting is in seconds and sits in `nimbus.toml`, in the current folder or your home folder. [1] For example: `poll_interval = 30`.
>
> To apply the change:
> - Changes to `nimbus.toml` take effect the next time Nimbus starts. If it runs as a background service, restart it with `nimbus service restart`. [2]
> - To test a value first, you can override it for a single run with the environment variable `NIMBUS_POLL_INTERVAL`, which takes priority over the file. [2]
>
> If you need changes right away after lengthening the interval, you can run `nimbus sync` manually. [3]
>
> The results don't say what value to choose beyond the 30-second default.

### mongodb-order-lines (all): Pass, top score 0.7004

**Q:** Should order line items go in the same record as the order, or in a separate table?

*Note in test-questions.json:* Embed; relational wording ('record', 'table').

> Per your uploads, line items should go in the same document as the order (embedded), not in a separate collection.
>
> - Embed when the related data is read together with the parent most of the time, it belongs to the parent and has no life of its own (an order's line items, a person's addresses), and the number of related items is small and bounded. [1] Order line items are given as an example of this case.
> - The document model's main rule is that data that is accessed together should be stored together [2]. Reading the order then takes one lookup by `_id`, with no joins. [2]
> - The example order stores its line items in an `items` array inside the order document. In a relational database the same order would usually span three tables (orders, order_items, customers) and need joins to read back. [3]
>
> A separate table (or collection) is better when the data is highly interconnected and queried in many unpredictable ways, or when most operations need to update many entities at once in transactions [4]. Referencing also makes sense if the related items can grow without limit [1], which the uploads don't suggest is typical for line items.

### mongodb-order-lines (one): Pass, top score 0.7004

**Q:** Should order line items go in the same record as the order, or in a separate table?

*Note in test-questions.json:* Embed; relational wording ('record', 'table').

> In MongoDB's document model, line items should go in the same document as the order, embedded rather than in a separate collection (the equivalent of a table).
>
> - **The embed guidance:** Embed when the related data is read together with the parent most of the time, when it belongs to the parent and has no life of its own (an order's line items are given as an example), and when the number of related items is small and bounded. [1]
> - **Read efficiency:** The main rule of document design is that data accessed together should be stored together. Reading the order takes one lookup by `_id`, with no joins. [2]
> - **Contrast with relational:** In a relational database the same order would usually span three tables (orders, order_items, customers) and need joins to read back. [3]
>
> If a line item's product data is large, shared, or needs to be read on its own, a reference may fit better. One middle ground is the extended reference pattern: store the `_id` plus the few fields you display most often, such as a product's name and price. The cost is that copied fields must be updated in both places if they change. [1]
>
> If you're using a relational database instead, the uploads don't say how to model line items there beyond the three-table example above.

> - To sign in, go to your project folder and type `claude`. The first time, it opens a browser window to log in with your Claude account, or you can choose to use an API key from the Console. [2]
