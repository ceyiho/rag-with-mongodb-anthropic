### guide-battery (all): Pass

**Q:** My laptop battery drains fast because Nimbus checks for changes too often. What can I change?

*Note in test-questions.json:* poll_interval in nimbus.toml; never says 'poll'.

> Raise the `poll_interval` setting in `nimbus.toml`, which controls how often Nimbus asks the server for remote changes. [1] Lower values make changes appear sooner but use more battery and bandwidth, and the default is 30 seconds. [1] A higher value than 30 means fewer checks and less battery use.
>
> Example:
> ```toml
> poll_interval = 120
> ```
>
> Some practical points:
> - Changes to `nimbus.toml` take effect the next time Nimbus starts. If it runs as a background service, restart it with `nimbus service restart`. [2]
> - To test a value first, use an environment variable such as NIMBUS_POLL_INTERVAL, which takes priority over the file. [2]
> - Nimbus looks for a `nimbus.toml` in the current folder first and falls back to the one in your home folder [1], so make sure you edit the file that is actually in use.
> - If you need changes immediately, you can run "nimbus sync" manually. [3]

### handbook-changes-not-seen (all): Pass

**Q:** A colleague edits files but nobody else sees the changes. Why?

*Note in test-questions.json:* Most common support request: viewer permission, exclude pattern, or conflict.

> The handbook lists three likely causes:
>
> 1. **Viewer permission.** In most cases the member has viewer permission on the folder, so the CLI is syncing it in read-only mode and quietly keeping their edits local. [1] Check their permission on the folder first. [1] This fits the permissions model: viewers can download files but cannot change them, and the CLI syncs viewer folders in read-only mode, so local edits are never uploaded. [2]
>
> 2. **An exclude pattern.** An exclude pattern in their nimbus.toml file may match the files they are editing; ask them to run "nimbus status --why" followed by the file name, which prints the rule that stopped the upload. [1]
>
> 3. **A sync conflict.** If the same file was changed by two people between syncs, Nimbus keeps both copies and saves the other version next to the original with ".remote" added before the extension, logging error NMB-4012. The member may be looking at the wrong copy. [1] In this case the local file keeps its name, and nothing is actually lost. [3]

### handbook-storage-full (all): Pass

**Q:** What happens when the workspace runs out of storage?

*Note in test-questions.json:* Uploads stop with NMB-3007; downloads and deletes keep working.

> Storage is shared by the whole workspace. When usage reaches 90 percent of the limit, owners and administrators receive an email warning. At 100 percent, uploads stop and the CLI reports error NMB-3007 for every file it tries to upload. Downloads and deletes keep working so members can free up space. [1]
>
> Ways to free space:
> - Files in the trash count toward the limit until removed permanently, which happens automatically after 30 days. You can empty the trash from the Storage page to free space immediately. [1]
> - Old file versions also count toward the limit. Nimbus keeps every version for 90 days by default, and you can shorten this to 30 days on the Storage page, which usually frees a large amount of space in workspaces with frequently edited files. [1]

### handbook-subfolder-access (all): Pass

**Q:** Why did people lose access to a subfolder after I added editors to it?

*Note in test-questions.json:* Subfolder settings replace inherited ones completely.

> Permissions are inherited by subfolders unless a subfolder has its own settings. In that case, the subfolder's settings replace the inherited ones completely rather than adding to them. [1] For read-heavy workloads with a clear access pattern, one document per read is simpler and usually faster. [1]
>
> - **Documents map to objects in code:** A document looks like the object your application already works with, so no object-relational mapping layer is needed to translate between rows and nested objects. This removes a whole category of code and bugs. [2]
>

>
> - **Horizontal scaling:** MongoDB scales out by sharding, splitting a collection across servers by a shard key. Because related data sits in one document, most operations touch one shard. [4] Scaling a relational database across servers is possible but harder, because joins and foreign keys assume the rows live together. [4]
>
> The uploads also note that relational databases remain a strong choice when data is highly interconnected and queried in many unpredictable ways, when most operations need to update many entities at once in transactions, or when a team relies on existing SQL tooling and reporting. [5]

>

>
> **Check it worked**
> - Run `claude --version` to check the install, and `claude doctor` if something looks wrong. [1] The native installation updates itself in the background. [1]
>

> - Go to your project folder and type `claude`. The first time, it opens a browser window to log in with your Claude account, or you can choose to use an API key from the Console. [2]
